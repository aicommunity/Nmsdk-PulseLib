# Владение состоянием поиска одного входа

## Область изменения

`BoundedTrainingSession::InputSearchState` объединяет уже существовавшие поля
локального поиска. Это механическое выделение состояния, предшествующее
изменению порядка обхода входов. Математическая цель, параметры, бюджеты,
схемы архивов и публичный интерфейс контроллера остаются прежними.

Текущая реализация завершает локальный поиск входа до `AdvanceInput()`:
Classic посещает обучаемые входы в возрастающем порядке, Branch — в обратном.
Один такой визит может потребовать нескольких пар измерений и изменений
структуры. Выделение `InputSearchState` само по себе не вводит циклического
чередования входов Classic.

## Границы владения

| Состояние | Владелец | Причина |
|---|---|---|
| Фоновая модель при начале локального поиска | `InputSearchState` | Относительно неё формируются текущие кандидаты |
| Счётчик локальных кандидатов и выбранный лучший кандидат | `InputSearchState` | Относятся к поиску одного входа на данном фоне |
| Курсоры L/Ns/Rs, контексты C и их очерёдность | `InputSearchState` | Описывают перечисление локальных кандидатов |
| Выданные совместные кандидаты и локальные измерения | `InputSearchState` | Используются при локальном ранжировании |
| Фактическая текущая модель, revision и epoch | `BoundedTrainingSession` | Любое физическое изменение относится ко всему графу |
| Бюджеты проб, изменений и невалидных наблюдений | `BoundedTrainingSession` | Не возобновляются при смене входа или C-контекста |
| Лимит N0-предложений длины на вход | Общая карта с ключом входа | Не возобновляется при новом sweep или C-контексте |
| Pending/armed-действие, anchor и защита от повторной выдачи | `BoundedTrainingSession` | Незавершённую пробу нельзя переносить между входами |
| История доказательств и последняя измеренная выбранная граница | `BoundedTrainingSession` | Должны оставаться доступны адаптеру после смены входа |
| Независимая финальная проверка всех входов | `FinalVerificationSession` | Локальный выбор кандидата не доказывает Exact |

## Ограничение будущего циклического обхода

Локальное состояние не является checkpoint физической модели. Если другой
вход изменил граф, сохранённые `fullParameters`, полная карта C, остатки,
bracket и ранги относятся к прежнему revision. Их нельзя применять как свежие
измерения новой модели. Сохранённый лучший кандидат может стать только
предложением: требуется применить разрешённые параметры текущего входа к
актуальному фону и выполнить новые anchor/input-измерения. Необходимо отдельно
сохранять индивидуальные поправки остальных путей и dormant C-пути.

Будущий вариант чередования должен иметь явный версионированный выбор режима,
сохранять воспроизводимость существующих конфигураций, общие ограничения
поиска и независимую финальную проверку. Механический коммит сам по себе
такого режима не вводил; отдельный последующий кандидат описан ниже.

## Отдельный кандидат ядра: ClassicCandidateRoundRobin

После механического выделения состояния подготовлен отдельный opt-in-кандидат
`InputTraversalPolicy::ClassicCandidateRoundRobin`. Значение по умолчанию
`Sequential` сохраняется. Первый кандидат ядра был намеренно закрыт для native
Start/import/export, пока выбор не сохранялся в кодеках. Следующий кандидат
добавляет общую декларацию `input_traversal` в cold-конфигурацию, runtime plan
и summary. Код ещё требует компиляционных и native-проверок; рекомендуемый
режим и совместимость с legacy этим не объявлены.

Единица кванта — полностью измеренный кандидат, включая пару anchor/input,
всю штатную пачку и требуемые повторы. `candidates_per_visit` явно задаёт число
таких кандидатов до переключения. Внутри незавершённой пробы переключения нет.
Classic посещает входы 0,…,M−2 по кругу; опорный M−1 остаётся фиксированным.
Branch сохраняет обратный последовательный порядок и отклоняет новый выбор.

```text
after a complete candidate:
    record actual observation and charge common budgets
    if locally exact or freshly remeasured final local proposal:
        mark this input locally finished
    if locally finished or declared visit quantum is exhausted:
        save this input's finite cursors and candidate count
        choose the next unfinished Classic input

on return after another model edit:
    keep finite enumeration positions and already charged allowances
    use CURRENT parameters and C corrections of all other inputs
    clear measured brackets, local ranks and effective resistance domains
    keep an old selected coordinate only as a proposal requiring new probes

after all local searches:
    perform fresh independent final verification of every input
```

Любое изменение epoch между визитами инвалидирует локальные измерения,
даже если скалярные L/Ns/Rs не изменились: мог измениться binding физического
preview. Публичная история сохраняет исходные revisions и не переписывается
под новый фон. Проекции разрешены только для перечислительных/предлагаемых
координат. Новый effective Rs domain запрашивается у адаптера заново.

Исторический лучший кандидат после смены фона не ранжируется как свежий.
Если новый поиск исчерпан, его собственные координаты могут быть предъявлены
повторно; параметры остальных входов сохраняются текущими. Для C используется
`RestoreClassicDendriteCapacitance`: сохраняются реальные поправки остальных
путей, включая dormant-сегменты и соседние имена `Dendrite1_`/`Dendrite10_`.
Потеря истории путей, смена C0 origin либо политики остаются ошибками.

Бюджеты проб, edits, invalid, N0-предложений длины не возобновляются при
переключении. Кандидатный лимит хранится на вход до конца sweep. Новый sweep
разрешается только общей политикой после отрицательной полной проверки.
`maximumTraversalSeedElements` ограничивает суммарный начальный запас L/Ns/Rs
в сохранённых входных/C-курсорах; история отдельно ограничена бюджетами проб.

Такой квант отличается от legacy-переключения по отдельным пачкам. Его
научный эффект необходимо измерить отдельно. Подготовлены адресные decision
сценарии M=1,2,4,6, нормализаций Ns/Rs, повторов, C-контекстов, общего бюджета, fresh final
gate и смены фона. Компиляция, выполнение, native-подключение, сериализация
нового выбора и физическое сравнение ещё не подтверждены.

## Проверка

Следующий кандидат кодеков сохраняет порядок явно:

```json
"input_traversal": {
  "kind": "timelearner_input_traversal",
  "schema_version": 1,
  "policy": "classic_candidate_round_robin",
  "candidates_per_visit": 3,
  "maximum_seed_elements": 131072
}
```

Поле находится в `search` cold/runtime-документа и в `configuration` summary.
Отсутствие означает прежний Sequential. Явный объект с no-op Sequential,
неизвестная версия, лишнее поле, bool вместо числа или неполная декларация
отклоняются. Размер визита положителен и не превышает кандидатный лимит входа.
Числа сохраняются точно в диапазоне JSON-count до2^53−1. Физика, captured
references, допуски и общие бюджеты от этого поля не меняются.

Квант1 остаётся допустимым вариантом. Однако после каждого чужого edit история
измерений очищается, а `ProposeMeasuredLength` требует3 различных свежих длин.
При кванте1 некоторые входы могут не накопить их. Квант3 позволяет сохранить
три измерения на одном фоне до переключения и сформировать предложение.
Это ограничение порядка поиска, не разрешение переносить старые остатки.
Для разных C-контекстов совместимость измеренной физики проверяется отдельно;
сам по себе размер визита не гарантирует прогноз или сходимость.

`InputTraversalJson.h` используется всеми C++-кодеками. Python-читатель
`input_traversal.py` проверяет тот же договор и связывает декларацию с effective
summary. В warm runtime plan сохраняется именно действующий размер визита;
его нельзя заменить значением первоначального cold-документа.

Новая проверка подготовлена отдельно от первого кандидата14:18 decision/codec
случаев и3 случая native-деклараций, без заявленного runtime-успеха.

Статическая проверка обратной подстановкой квалификатора `inputSearch.`
восстанавливает исходный `.cpp` побайтно, кроме исправленного комментария о
порядке обхода. Она не заменяет компиляцию. До приёмки необходимы сборка полных
production translation units до/после, одинаковый полный набор decision-тестов
и проверка native-интеграции с пересобранными зависимостями. Действующие опыты
используют прежний неизменяемый runtime; результат этих опытов не является
проверкой данного выделения состояния.
